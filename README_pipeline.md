# 히오스 영웅 백과사전 빌드

게임 원본에서 한글화된 백과사전 HTML 까지 한 번에 만든다.
**결과물은 [output/](output/) 폴더에만 있다.** 나머지 폴더는 만들어지는 과정이다.

---

## 실행

`실행.bat` 을 더블클릭하거나, 터미널에서:

```bash
python 00_scripts\pipeline.py --all
```

| 명령 | 하는 일 | 걸리는 시간 |
|---|---|---|
| `--all` | 1~7 전부. 게임이 패치됐을 때 | 약 4분 |
| (없음) | 3·5·6·7 만. 받아온 데이터로 다시 빌드 | 약 20초 |
| `--all --check` | 필요한 게 다 있는지만 확인 | 즉시 |
| `--all --dry-run` | 실행 없이 계획만 출력 | 즉시 |
| `--from 6` | 6단계부터 끝까지 | |
| `--only 6,7` | 지정한 단계만 (번호·이름 아무거나) | |

기본 실행에 1·2·4 가 빠져 있는 이유는 그 셋만 바깥에 나가기 때문이다 — 1·2 는
CASC 를 읽고 4 는 위키 API 를 90번 두드린다. 게임이 패치됐을 때만 `--all` 을 쓰면 된다.

### 필요한 것

- **Python 3** + `requests` (`pip install requests`)
- **`dotnet-heroes-data-parser.exe`** — PATH 에 있어야 한다
- **히오스 설치** — 있으면 로컬에서 읽어 훨씬 빠르다. 없으면 자동으로 온라인 CASC 로 넘어간다

`python 00_scripts\pipeline.py --all --check` 로 한 번에 확인할 수 있다.
4분짜리 작업이 중간에 죽는 대신 시작 전에 멈춘다.

적는다. 위키는 사람이 손으로 적는 곳이라 패치를 놓치거나 칸을 헷갈릴 수 있고,
게임 데이터는 게임 그 자체라 틀릴 수 없다.

| 맞대는 칸 | 게임 쪽 출처 |
|---|---|
| 재사용 대기시간 | 게임이 띄우는 값(HDP 툴팁) + `Cost/Cooldown@TimeUse` |
| 자원 소모 | 게임이 띄우는 값(HDP 툴팁) + `Cost/Vital@value` |
| 레벨당 성장률 | 게임 툴팁의 `(+4% per level)` |
| 범위 그림 치수 | 스킬 이름으로 시작하는 정의들의 길이·각도 |
| 시전 시간 | `CastIntroTime` + `CastOutroTime` |
| 틱 주기 | `PeriodicPeriodArray` 의 역수 |
| 투사체 속도 | `Speed` / `SpeedMax` |
| 소환물·무기 스탯 | `CUnit`(Radius·SightRadius·LifeMax·Speed) / `CWeapon`(Range·Period) |
| 영웅 충돌·피격 반지름 | `CUnit/Radius`, `CUnit/InnerRadius` |

무엇이 있는지부터 알아야 검증을 설계할 수 있어서, 위키가 주는 것을 전부 세는
[wiki_inventory.py](00_scripts/wiki_inventory.py) 도 함께 둔다
(→ [07_auto_localized/wiki_inventory.md](07_auto_localized/wiki_inventory.md)).

리포트의 각 줄에는 **XML 의 어느 정의·태그·파일**에서 읽었는지 적혀 있어 직접
열어 확인할 수 있다. 안 맞는 값은 성격별로 갈라 둔다 — `확인 필요` 가 진짜로
봐야 할 것이고, `위키 칸 헷갈림`·`충전형 표기 차이`·`반올림 차이` 는 이유가
밝혀진 것들이다.

```bash
python 00_scripts\pipeline.py --only verify --strict
```

`--strict` 는 `확인 필요` 가 있을 때만 오류로 끝낸다. 반올림 같은 걸로 빌드가
깨지면 안 되기 때문이다.

3단계는 같은 원본을 두 가지로 내놓는다. 앞의 둘은 뒤 단계가 읽고, `_` 로 시작하는
둘은 사람이 열어보는 용도다.

| 안쪽 폴더 | 무엇 |
|---|---|
| `kokr/` `enus/` | 원본 구조를 살린 영웅별 폴더 — **이후 단계가 읽는 것** |
| `_by_hero/` | 영웅당 대표 XML 한 장 (`abathur.xml` … 89개) |
| `_merged/` | 게임스트링을 로케일별 한 파일로 합친 것 + 수집·충돌 로그 |

`output/` 에 결과물 아닌 파일이 생기면 빌드가 알려준다.

경로는 [00_scripts/paths.py](00_scripts/paths.py) 한 곳에서 정한다. 폴더 이름을
바꾸려면 거기만 고치면 된다.

### 손으로 고치는 곳은 하나뿐

| | 폴더 | 빌드가 하는 일 |
|---|---|---|
| **내가 정한 것** | [00_manual/](00_manual/) | **읽기만 한다** |
| 뽑아낸 것 | 01~07 · output | 매번 통째로 다시 만든다 |

01~07 안을 고치면 다음 빌드에 날아간다. 자세한 것은

| 파일 | 무엇 |
|---|---|
| `glossary.json` | 위키 상세 필드의 한글 표기 214개 |
| `aoe_overrides.json` | 범위 그림 수동 보정·평타 광역·그리지 않을 목록 |
| `name_overrides.json` | 스킬 이름 ↔ 게임 문자열 짝짓기 |
| `passive_flags.json` | 액티브/패시브 표시 스냅숏 |
| `settings.json` | 사이트 링크·크기 기준자·그리기 옵션 |

수동 항목은 자동으로 뽑은 것 위에 덮어쓰고, **붙일 곳을 못 찾으면 빌드가 경고한다.**
그림 상세 표에도 `출처: 손으로 넣은 값` 줄이 붙어 어느 쪽인지 바로 보인다.

## 단계별로 무슨 일이 일어나는가

### 1 casc — 게임 데이터 추출

```
dotnet-heroes-data-parser casc-extract game -o 01_auto_casc -i ...
```

게임플레이 XML 과 한/영 게임스트링만 골라 꺼낸다.

포함 패턴을 `*data.xml` 로 좁히면 안 된다. 영웅 정의 파일 중 `garrosh.xml`,
`kelthuzad.xml` 처럼 `data` 로 끝나지 않는 것이 있어 **그 두 영웅이 통째로 빠진다.**
`core` 의 기본값 XML 도 있어야 프로필 파서가 상속값을 풀 수 있다.

### 2 herodata — 영웅 JSON 과 아이콘

```
dotnet-heroes-data-parser game -e Hero:images -l enUS -l koKR \
    -g ColoredTextWithScaling --gs-replace-constant-vars -o 02_auto_herodata
```

**`casc-extract` 는 이걸 만들지 않는다.** 원본 파일만 꺼낸다. 영웅 JSON 과 이미지는
최상위 명령의 `Hero` 추출기가 만든다 — 그래서 1·2 가 별개의 단계다.

추출 형식도 중요하다. 백과사전 템플릿은 `184 (+4% per level)` 꼴을 정규식으로 읽어
레벨별 수치를 다시 계산하는데, 기본 `RawText` 로 뽑으면 그 문구가 없어 **성장 표기가
통째로 죽는다.**

### 3 analysis — 영웅별로 재배치

흩어진 `mods/` 를 `_core` / `_strings` / `heroes/<영웅>/` 구조로 다시 묶는다.
한국어·영어를 각각 만든다.

### 4 wiki — Fandom 수집

MediaWiki API 로 90명의 스킬·특성 원문을 받는다. 요청 사이에 1.5초씩 쉬므로
2분 30초쯤 걸린다 (`--delay` 로 조정).

### 5 profile — XML + 위키 합치기

게임 XML 의 수치와 위키의 설명을 영웅별 프로필 JSON 으로 합친다.

### 6 build — 백과사전 생성

HDP 5.x 출력을 구형 스키마로 옮긴 뒤([adapt_herodata.py](00_scripts/adapt_herodata.py))
생성기를 돌린다. 4MB 짜리 결과물을 통째로 갈아끼우므로 직전 것을 `.html.bak` 으로
남긴다.

### 7 kr — 한글화와 주입

게임스트링으로 이름·설명을 한글화하고([localize.py](00_scripts/localize.py)),
위키 상세 필드와 범위 그림을 백과사전에 심는다([inject_wiki.py](00_scripts/inject_wiki.py)).

## 백과사전에 들어가는 것

### 한글화

번역하지 않는다 — 블리자드가 이미 번역해 둔 문자열을 되찾아 붙인다.
**딱 하나 예외가 스킬·특성 하단의 위키 상세 필드다.** 그건 위키 편집자가 영어로
붙인 값이라 게임에 대응하는 한글이 없어 표기를 직접 정했고, 그 목록이 용어집이다.

- **이름 2530/2530 (100%)** — 위키 영문 표기로 enus 를 역인덱스해 내부 키를 얻고,
  같은 키의 kokr 값을 쓴다
- **설명 99.4%** — 같은 키의 한글 툴팁. 수치는 `<d ref="..."/>` 참조 경로로 짝지어
  채운다. **한글은 어순이 달라 자리 순서로 넣으면 값이 뒤바뀐다**
- **메타 필드** — 위키 편집자가 붙인 값이라 gamestring 에 없다.
  [glossary.json](00_manual/glossary.json) 용어집으로 옮긴다. 그 전체는 백과사전
  **좌측 상단 `📘 용어집`** 버튼으로 볼 수 있다 (별도 파일이 아니라 안에 심는다)

검수가 필요한 항목은 [07_auto_localized/report.md](07_auto_localized/report.md) 에 모아 둔다.

### 레벨 0

패치노트가 0레벨 기준이라 데이터 원값이 Lv0 에 오도록 곡선을 한 칸 밀었다.

```
값(lv) = 기본값 x (1+성장률)^lv      Lv0 = 1365, Lv1 = 1420
```

### 기본 공격 유형

| 구분 | 근거 |
|---|---|
| 근접 / 원거리 | `<Options index="Melee">` |
| 즉발 / 투사체 | 이펙트 체인의 `CEffectLaunchMissile` |
| 광역 | **기본 평타에는 없다.** 전부 특성으로 붙어서 `광역 가능(특성)` 으로 표시 |

### 범위 그림

범위 공격 423개를 실척 평면도로 그린다. 스킬 아이콘이나 `◎ 범위 보기` 를 누르면
큰 창으로 뜬다.

| 모양 | 개수 | 근거 |
|---|---|---|
| 원형 | 254 | `aoe=Circle` + radius |
| **관통 경로** | **84** | **`hitbox` — 아래 참고** |
| 부채꼴 | 45 | `aoe=Radial`, 또는 `aoe` 없이 radius+arc 만 있어도 부채꼴 |
| **복합** | **8** | `- A: X - B: Y` 를 이름표로 갈라 겹쳐 그린다 |
| 직사각형 | 26 | `aoe=Rectangle` + width + height |
| 삼각형 | 3 | `width` 가 한 변의 길이 (데커드 봉인의 두루마리) |
| 고리 | 3 | 한복판이 비어 있을 때만 |
| 사다리꼴 | 1 | 앞뒤 폭이 다를 때 (D.Va 방어 매트릭스, 리밍 비전 보주) |
| 정사각형 | 1 | 높이를 안 적어 `width` 를 양쪽에 쓴다 (데커드 호라드림의 함) |

### 돌진·논타겟은 hitbox 로 그린다

돌진이나 관통기는 `aoe` 가 비어 있는 대신 `hitbox` 가 `"3.0 x 3.0"` 처럼 적혀 있다.
이 두 수치가 각각 뭔지가 관건인데, 데스윙 대격변이 답을 준다 —
`aoe=Rectangle · width=9.0` 인데 `hitbox=9.0 x 3.0` 이다.

> **앞 수치 = 진행 방향에 수직인 폭, 뒤 수치 = 투사체 자체의 앞뒤 두께**

그래서 시전자에서 사거리 끝까지 **훑고 지나간 자리**를 폭만큼 채우고, 도착점의
투사체 판정 상자를 노란 점선으로 겹친다.

`- Min: 3 - Max: 18.25` 처럼 최소·최대가 같이 적힌 사거리는 최대를 쓴다. 첫 숫자를
집으면 알라라크 죽음의 돌진이 3 짜리 경로로 그려진다.

### 도형이 여럿인 스킬

`aoe` 가 `- Slam: Circle - Shockwave: Rectangle` 처럼 적힌 스킬이 8개 있다.
이름표가 도형과 치수를 묶어 주므로 (`radius=2.5 (slam)`,
`range=- Slam: 2.5 - Shockwave: 17`) 조각별로 나눠 색을 달리해 겹쳐 그린다.

들창코 충격파·케리건 원시 손아귀·그레이메인 잔혹한 할퀴기·오르페아 두려움 등이
여기 해당한다.

### 안팎이 갈리는 스킬

`반경`에 `- Inner: A - Outer: B` 가 적힌 스킬은 대개 **안과 밖의 효과가 다르다.**
가운데는 기절, 바깥은 끌어당김 하는 식이다. 그래서 기본은 **안쪽 원 + 바깥 고리**
두 겹으로 그린다.

한복판이 정말 비어서 아무 일도 없는 경우에만 속 빈 고리 하나로 그린다. 이건 위키
비고의 `not affected in any way` 문구로 가려낸다 (제이나 서리 고리, 메피스토 번개 회오리).

각도까지 있으면 고리 부채꼴이 된다 (가로쉬 땅의 파괴자 45도, 누더기 지면 강타 70도).
구역별로 무슨 효과인지는 [00_manual/aoe_overrides.json](00_manual/aoe_overrides.json)
에 이름을 달아 둔다.

### 위키 표기가 틀린 경우

`aoe=Circle` 인데 `arc`(각도)가 같이 적힌 스킬이 있다. 각도는 원에 쓸 수 없는 값이라
표기 쪽이 틀린 것이다 — 알렉스트라자 폭풍 날개(50도), 요한나 눈부신 방패(35도) 둘 다
실제로는 부채꼴이다. 부채꼴로 그리고 상세 표에 `도형 보정` 줄을 넣어 근거를 밝힌다.

여러 모양이 섞인 표기(`- End: Radial - Bite: Circle`)는 여전히 그리지 않는다.

### 연달아 떨어지는 스킬

굴단 부패·크로미 용의 숨결처럼 한 번 시전에 같은 범위가 여러 번 떨어지는 것들이다.
개수는 `aoe` 의 `Circle (x3)` 이나 설명문의 `three bursts` / `3 blasts` 에서, 간격은
`* spacing` 항목에서 읽어 시전 방향으로 늘어놓고 순서를 번호로 찍는다.

**둘 다 있어야만 그린다.** 간격을 모르면 어디에 놓을지 알 수 없고, 개수를 모르면
몇 개인지 알 수 없다. 간격이 각도로 적힌 것(디아블로 화염 발구르기 `20 degrees`)은
일렬이 아니므로 제외한다.

### 여러 갈래로 나가는 스킬

겐지 수리검처럼 한 번에 여러 발이 퍼지는 스킬은 비고에 각도가 적혀 있다.

> Shuriken at the edges are aligned **10 degrees to both sides** from the target point.

이 문구에서 각도를, 설명문의 `Throw 3 Shuriken` 에서 갈래 수를 읽어 −10°/0°/+10° 로
경로를 돌려 그린다. **문구가 없으면 한 갈래로 그린다** — 갈래 수를 알 길이 없는데
지어내면 그림이 거짓말을 한다. 현재 이 문구를 가진 스킬은 겐지 수리검 하나뿐이다.

투사체는 시전자에게서 생겨 앞으로만 나가므로 **경로가 뒤쪽으로는 뻗지 않는다.**
앞쪽으로만 판정 두께의 절반을 더 그린다.

**길이 단위는 전부 같다.** 시전자 반지름·사거리·범위 반경이 모두 같은 좌표계
(SC2 월드 유닛)에서 나온다.

**다만 기준점은 스킬마다 다르다.** 사거리를 시전자 중심에서 재는지 몸통 가장자리에서
재는지가 XML 의 `RangeUseCasterRadius` 에 박혀 있다. 차이는 딱 시전자 반지름만큼이라
시전자 원을 같이 그려 눈으로 가늠하게 한다.

- 격자는 시전자에 맞춰 깔아 **중심이 격자 교차점에 정확히 놓인다**
- 아래쪽 눈금자는 크기 기준을 그대로 잰다 — `|————| 레이너 평타 사거리(6.5)`,
  더 큰 그림이면 `해머 공성 모드 사거리(11)`
- 사거리가 없는 스킬은 왜 없는지를 적는다 (자기 중심 103 / 부모 스킬을 따름 68 /
  위키에 없음 19). 숫자를 지어내지 않는다
